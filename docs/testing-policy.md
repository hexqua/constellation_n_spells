# テスト設計方針

この文書は、テストを追加・整理するときの判断基準を定める。実行コマンド、変更に応じた検証、失敗時の報告手順は [AGENTS.md](../AGENTS.md#実行と検証) に従う。

## 優先する検証

実プレイのリグレッションを検出できる処理結果、状態遷移、Minecraft・依存 MOD・データとの接続を優先する。

- 採掘によるドロップと経験値、レシピの選択と完成品、ダメージや弾の衝突など、実際に起きる結果を確認する。
- 装備・交換・解除、保存・読込、処理の開始・中止など、状態が変わった後の結果を確認する。
- タグによる素材判定、系統や属性の解決、バイオームへの生成設定の反映など、定義が利用先へ接続されていることを確認する。
- 修理素材やエンチャント適性など、プレイヤーが利用する機能の成立条件を確認する。

すべてを通常のプレイヤー操作から再現する必要はない。検出したい不具合に必要な経路を通し、テスト名・assertion・コメントで保証範囲を伝える。

## 定数・getter・登録

硬度、爆破耐性、音、耐久値、レアリティ、精錬時間など、設定した値を getter で読み返して完全一致を要求するだけの検証は原則追加しない。実装と期待値を機械的に同時更新するだけのテストを増やさない。

ただし、定数を含む assertion 自体を禁止するものではない。完成品の出力個数、実際に得られる経験値、装備後の補正量など、守りたい処理結果の数値は検証してよい。特定の設定値自体を固定する必要がある場合は、意図しない変更で起きる不具合と、その値を守る理由を明確にする。

コンテンツの総数や単純な登録存在を網羅的に確認するテストは追加しない。レシピ選択、タグ解決、ブロックとアイテムの対応など、利用経路での接続を確認する。起動時や既存テストで検出できる欠落を重複して確認するだけのテストは避ける。

## Attribute の反映

modifier の属性・演算・量の定義を確認するだけで終えず、装備などの処理を通した後の entity の実際の属性値を確認する。

- 正しい部位への装備で反映され、手に持っただけでは反映されないこと。
- 交換・再装備で重複せず、解除すると元に戻ること。
- 複数部位、混成装備、強化済みアイテムなど、機能に応じた組み合わせでも正しく反映されること。

必要なケースは変更の影響範囲に合わせて選ぶ。期待値は実装の modifier から再計算するだけにせず、守りたい結果から定める。演算の違いを検出したい場合は、基礎値や併用する補正も区別できる条件にする。

FakePlayer の空 tick など、テスト用 entity が通常の更新を行わない場合は、必要な更新経路を通せる mock player 等を使う。

## 必須依存と optional MOD

必須 MOD の欠落は起動や他の機能テストで検出されるため、ロード確認だけの重複検証は追加しない。

optional MOD の検証構成では、起動プロファイルが要求する MOD のロードを確認する。対象 MOD が不在で連携処理を通らないまま成功することを防ぐ。

標準構成で optional MOD の検証を省略して成功するテストは、対象 MOD を含む構成での実行が必要である。省略された成功を連携機能の検証済みとして扱わない。

## 乱数とテストの安定性

有限回の試行で最大値などの特定結果が必ず出ることを要求しない。乱数に関係なく成立する範囲・不変条件を検証するか、必要な状態を明示的に再現する。

固定 seed は再現性を高めるが、有限サンプルで特定結果の出現を要求する検証の代わりにはならない。発生確率自体を検証する必要がある場合は、その目的と判定方法を別途設計する。

実行順序や共有状態に依存しないようにし、変更した状態や登録したリスナーは適切に復元・解除する。非同期処理は必要な完了条件と待機期限を定める。

## テスト用ヘルパーと経験値オーブ

誤ると検証漏れや不安定な失敗を生む集計・観測処理は、その前提を説明・保証する小さなテストを残してよい。製品機能のテストも同じヘルパーを使い、説明用テストと実際の観測方法が乖離しないようにする。

経験値オーブは、同額のオーブが統合されると entity 数が減り、value は変わらず count が増える。合計経験値は各オーブの value × count の総和として求める。entity 数や value の合計だけで判定すると、統合の有無によってテストが失敗する。

この前提の検証では、統合自体をランダムに発生させず、統合状態を直接再現する。例えば、次のケースを確認する。

- 未統合の 3 XP オーブ2個と、count が2の 3 XP オーブ1個が、どちらも 6 XP として集計される。
- 統合済みの 6 XP と未統合の 1 XP が混在しても、合計が 7 XP になる。

これは集計処理の検証であり、Minecraft 自身の統合処理や乱数依存の失敗全般を保証するものではない。現在は採掘テスト内に置き、別機能でも必要になった時点で共通化を検討する。

## 検証範囲と追加時の判断

処理の直接呼び出し、実際のイベント経由、実通信、client 操作は保証範囲が異なる。例えば、Codec の往復と client 状態更新の直接検証だけでは、実通信や切断イベントの接続まで検証したことにはならない。client 表示・入力等の手動確認が必要な場合は AGENTS.md の報告手順に従う。

追加・整理の際は次を確認する。

1. どんな不具合が起きると、このテストが失敗するか。
2. その不具合は、既存テストや起動時チェックでも検出できるか。
3. 正常な仕様変更、乱数、実行順序によって不要な失敗が起きないか。

テスト件数を維持・増加させること自体を目的にせず、検出できる不具合と保守負担から追加・統合・削除を判断する。
