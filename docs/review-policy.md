# レビュー方針

参照元の共通レビュー方針を本リポジトリへ適用する。

### Skill の使い分け
- コミット前の staged / unstaged / untracked 差分または指定コミットは `.codex/skills/review-local-change` でレビューする。
- base branch に対する機能ブランチ全体、PR、CI、Codex Cloud、人間レビューを含む readiness は `.codex/skills/review-feature-branch` で確認する。
- どちらの Skill もデフォルトではレビュー結果の報告だけを行い、明示指示なしに修正、stage、commit、push、PR コメント、merge を行わない。
- コードレビューでは、実行時・ビルド時・データ上の不具合を実装 Finding として優先する。PR 説明、リリースノート、移行ガイド、コミット構成、検証未実行などの運用・文書上の不足だけを実装 Finding にせず、重大な実装不具合を省略する理由にしない。
- ローカル変更レビューでは運用・文書上の不足をデフォルトで報告対象外とする。機能ブランチレビューで必要な場合だけ独立した Note とし、P3 相当を上限として readiness を下げない。

### 常設レビュー規則
- 追加・変更した要素は既存の registry 構成と EventBus 初期化へ登録し、未登録のままにしない。
- client 専用参照は client 初期化または適切な実行環境境界へ隔離し、専用サーバーから読み込まれる共通コードへ追加しない。
- client 由来の入力は不正値を想定するが、client の視線・選択結果を server 側で完全再現することは一律に要求しない。射程、権限・所有権、対象の有効性、置換・破壊可否、コスト、影響範囲など、server が守るべき制約の突破と具体的な実害で判断する。
- UX のため意図的に client / server 間の差を許容する変更では、許容する挙動と拒否すべき境界の両方を GameTest で明示する。重要な server 側制約が守られた既存仕様として確認できる場合は厳格化を修正方針にせず、テスト不足は検証状況または残余リスクとして示す。判断できない挙動をテスト追加だけで仕様化しない。
- ワールド・アイテム・プレイヤーの保存データと、それらが参照する content ID は、既存資産を失わないよう後方互換または migration を実装する。ベータ期間・正式リリース後とも共通とし、リワークでも収納物・装着物などの資産を保護する。
- lang キー、モデル・テクスチャ等のパス、レシピ・タグ、データパック定義などのリソース構成は、バランス調整・リワーク・実装整理に伴う意図した破壊的変更を正式リリース後も許容する。旧キー・旧パス・旧形式の維持や互換変換は一律に要求しない。
  - 外部のリソースパック・データパックの修正が必要になる変更は、PR 内で変更内容と主要な影響を簡潔に申し送る。ユーザー要求・変更説明から意図が分かる場合、別途「破壊的変更」という定型宣言は不要とする。通常のバランス変更まで破壊的変更として申し送ることは要求しない。
  - 個別キーの対応表、移行先の網羅、「移行先なし」の個別記載、専用の移行ガイドは必須としない。
  - リリースノートには、プレイ上の主要な変更や利用者に必要な作業がある場合に要点をまとめる。PR の申し送りを項目ごとに転記することは要求しない。
  - リソース配下の変更でも、保存済み資産の消失・破損や既存ワールドの読込不能につながる場合は、保存データの保護規則を適用する。ファイルの所在だけで互換性保護の要否を判断しない。
- 一般的なバランス・表示設定は、意図した改名・削除・既定値変更を許容し、互換変換を一律に要求しない。再設定が必要な場合は PR 内で主要な影響を簡潔に申し送る。権限・破壊許可・機能禁止などの管理設定は、旧設定が無視されて禁止操作が意図せず有効にならないよう保護する。
- 上記で許容する意図した変更について、互換変換や詳細な移行案内がないことだけでは実装 Finding、release blocker、readiness を下げる理由としない。申し送りの不足は運用・文書上の不足として扱う。意図しない互換性破壊、必要な資産保護の欠落、起動不能や権限制約の突破は、案内の有無とは切り離して具体的な実害に基づき判定する。
- generated/resource の削除・改名・出力パス変更では、旧出力の削除差分と target 側の再生成方針を追跡可能にし、stale 出力を残さない。
- 依存 MOD のバージョン条件は `gradle.properties`、`build.gradle`、`neoforge.mods.toml` で整合させる。TOML に固定上限がある場合、下限をその上限以上へ更新する変更では、同じ変更内で上限を撤廃または更新し、`build` と `runGameTestServer` を成功させる。
